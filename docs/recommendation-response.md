# 추천 응답 상세 정보

`POST /api/v1/recommendations`와 `GET /api/v1/recommendations/{id}`에 상세 필드를 추가한다.
명시된 중복 가능 혜택의 합산을 지원한다. 기존 미표시 데이터의 단일 혜택·순위·동률 규칙과 카드 상태 저장 구조는 유지한다.

## 기존 응답과 호환

카드 단위 `calculation`과 `remainingLimitAfter`는 유지한다.
`appliedRules`의 기존 `ruleId`, `description`, `benefitAmount`도 유지한다.

새 추천에는 다음 정보가 추가된다.

- `appliedRules[].calculation`: 적용 혜택별 계산식. 합산 시에도 개별 규칙의 최종 금액으로 한도 적용 여부를 판정한다.
- `appliedRules[].capGroupIds`: 해당 혜택의 한도부터 상위 한도까지 ID 목록. 같은 그룹을 중복 반환하지 않는다.
- `assumptions[].capGroupId`: 한도·횟수 가정이 가리키는 그룹 ID. 실적 가정은 null이다.
- `remainingLimitsAfter[]`: 금액 또는 횟수 제한이 있는 그룹별 상세 예측. 무제한 그룹만 있으면 빈 배열이다.

## 한도별 예측

| 필드 | 의미 |
| --- | --- |
| `capGroupId`, `description`, `capPeriod` | 추천 당시 한도 식별 정보 |
| `capAmount`, `capCount` | 전체 금액·횟수 제한. 제한 없으면 null |
| `remainingLimitBefore`, `remainingLimitAmount` | 계산에 사용한 결제 전 금액과 결제 후 예상 금액 |
| `remainingCountBefore`, `remainingCount` | 계산에 사용한 결제 전 횟수와 결제 후 예상 횟수 |
| `amountSource`, `countSource` | 각각 USER_INPUT / ESTIMATED / ASSUMED. 해당 제한 없으면 null |

모르는 금액·횟수는 전체 한도·횟수로 가정하되 저장된 카드 상태를 변경하지 않는다.
각 한도에 연결된 적용 혜택의 최종 금액만 합산해 차감한다. 공유 상위 한도는 전체 연결 혜택을 반영하고, 하위 한도는 해당 혜택만 반영한다.
여러 혜택이 같은 횟수 한도를 공유해도 한 거래의 횟수는 1회만 줄인다.
예측 잔여 값은 0 아래로 내려가지 않는다. 실제 결제 확인·차감 API는 이 변경에 포함하지 않는다.

## 질문 대상

실적 → 남은 금액 → 남은 횟수 순서, 같은 종류는 한도 ID 순서로 가정을 반환한다.
금액·횟수의 `affectsRank`는 지정한 그룹의 해당 미확인 값만 0으로 바꿔 추천 카드가 달라지는지 판정한다.
다른 그룹이나 같은 그룹의 다른 필드는 바꾸지 않는다. 기본 추천 계산에는 영향을 주지 않는다.

## 스냅샷과 이전 기록

새 상세 정보도 기존 jsonb 결과 스냅샷에 저장한다. GET은 저장된 결과만 사용한다.
카드 상태·규칙을 바꿔도 이전 추천을 다시 계산하지 않는다. DB 마이그레이션은 필요하지 않다.

확장 이전 기록은 기존 응답을 유지하며, 저장되지 않은 `remainingLimitsAfter`·`capGroupIds`는 빈 배열,
혜택별 `calculation`·가정의 `capGroupId`는 null이다. 현재 규칙으로 과거 정보를 추측하지 않는다.
따라서 빈 배열이 반드시 당시 한도 없음이라는 의미는 아니다. 과거 기록에는 상세 정보가 없을 수 있다.

## 명시적 중복 적용

- `benefit_rules.stackable`은 기본 `false`다. 기존 시드의 표시를 자동으로 켜지 않는다.
- 카드 데이터 담당자는 약관·출처로 함께 적용 가능함을 확인한 별도 혜택에만 `true`를 적재한다. 이미 기본+추가를 합친 요율이나 중복 불가 규칙은 표시하지 않는다. 문구·한도 ID로 자동 추론하지 않는다.
- 대상·유효기간·검증·조건·실적을 통과한 표시 규칙만 합산 후보가 된다. 미표시 규칙과 섞지 않고, 기존 단일 후보와 합산 후보 중 더 큰 금액을 고른다. 동률이면 가정이 적은 후보, 여전히 같으면 기존 단일 후보를 유지한다.
- 공유 한도 배분은 규칙을 단독 적용했을 때 금액 내림차순, 가정 수 오름차순, ID 오름차순으로 한다. 각 규칙별로 절사한 뒤 실제 배분된 금액을 합산한다. 적용 목록은 최종 금액 내림차순 → ID 오름차순이다.
- `appliedRules[].benefitAmount` 합계는 `expectedBenefit`과 같다. 0원 규칙은 적용 목록·차감·가정에 추가하지 않는다.
- 호환 필드 `calculation`은 대표 혜택(최종 금액 내림차순 → ID 오름차순)의 계산식이다. 여러 혜택 합계를 단일 비율로 표시하지 않는다. 호환 `remainingLimitAfter`는 대표 혜택에 연결된 금액 한도의 **합산 후** 최소 잔여다. 새 화면은 혜택별 계산식과 `remainingLimitsAfter[]`를 사용한다.
- 가정·질문은 실제 적용된 혜택의 대상으로 합치고 같은 `{ type, capGroupId }`를 한 번만 반환한다. 가정 변경에 따른 순위와 확인된 정보 추천도 같은 합산 엔진을 사용한다.
- 새 스냅샷의 한도별 집계 차감을 기존 결제 원장으로 전달한다. 실제 결제 확인·재전송·취소·복원과 사용자 재입력 우선 규칙은 유지한다.

실제 상품별 합산 표시 적재, 채널·결제수단 조건, 동률 연회비 기준 변경, 저장 전 미리보기, 질문 최대 2개 선택 UI는 별도 작업이다.
